# Benchmark de File Analyzer

Este experimento compara aplicaciones completas con módulos de análisis cargados en tiempo de ejecución y módulos de análisis enlazados directamente desde archivos objeto. Incorporar directamente el código objeto de los analizadores al ejecutable constituye un enlace estático de esos módulos. Ambos ejecutables conservan bibliotecas del sistema enlazadas dinámicamente. La aplicación original y sus fuentes permanecen intactas. Ambas compilaciones usan las fuentes originales de los analizadores; las copias anteriores en `static_app/analyzers` se conservan, pero no se utilizan para compilar los analizadores. La aplicación estática copia el menú, sustituye el descubrimiento de complementos por un registro fijo y explica que para volver a cargar es necesario recompilar. Las definiciones del compilador renombran los cuatro símbolos públicos de los analizadores con los prefijos `txt_`, `csv_` y `log_`. Ambas variantes usan las mismas opciones de optimización y código PIC para los analizadores; no se usa LTO ni `-static` global.

Desde este directorio ejecuta `make`, `make test` y `make run`. Se requieren Python 3, GCC, make y Linux. `make run` crea el conjunto de datos para una prueba rápida y utiliza dos calentamientos y diez mediciones. Para mediciones mayores, ejecuta `python3 tools/generate.py --preset medium` o `--preset heavy`, y después `python3 tools/benchmark.py`. Personaliza los valores con `--count`, `--bytes` y `--seed`; la cantidad es por formato y la configuración predeterminada de heavy produce aproximadamente 160 MB en total. Las opciones `--warmups` y `--trials` del ejecutor ajustan el muestreo. Los archivos generados están en este directorio; `make clean` los elimina.

El coordinador en Python prepara un mismo guion de entrada para cada carga de trabajo e invoca al ejecutor en C. Este usa fork, exec, tiempo monotónico y wait4, redirige la salida a archivos y registra el RSS máximo. Después de cada ejecución se comprueba que la salida medida no contenga archivos omitidos ni errores de análisis. Antes de medir, se comparan los informes completos de cada archivo generado y del ejemplo LOG, incluida la comprobación de archivos omitidos y errores reportados. Las ejecuciones alternan el orden y usan un proceso nuevo para cada muestra. El CSV de datos brutos contiene cantidad de archivos, bytes, MB/s decimales, RSS en KiB, tamaño del ejecutable y tamaño total de las bibliotecas de analizadores; `library_bytes` es cero para la versión estática porque su código de análisis está incluido en el ejecutable, y es la suma de los tamaños de los complementos para la dinámica. El CSV de resumen contiene estadísticas de tiempos. La diferencia impresa es dinámica menos estática, relativa a la estática. El tiempo incluye inicio, carga, manejo del menú, E/S, análisis, salida y limpieza; no puede atribuirse únicamente a la carga.

El RSS incluye páginas compartidas y no equivale a memoria física exclusiva. Los tamaños del ejecutable y de los complementos incluyen distintos metadatos y no equivalen directamente al espacio instalado. El calentamiento de la caché, la planificación de la CPU, los procesos en segundo plano y la virtualización de WSL afectan los resultados; repite las pruebas en condiciones controladas e informa el entorno y la variabilidad. En WSL, prefiere el sistema de archivos de Linux a `/mnt/c`. Los datos generados son sintéticos y los resultados podrían no generalizarse. La aplicación original informa los errores de análisis en stdout y puede salir con código cero; la validación comprueba esos mensajes, por lo que el coordinador también inspecciona la salida medida. Ningún resultado debe considerarse válido si las entradas cambian entre la validación y la medición.
